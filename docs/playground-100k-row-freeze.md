# 10만 행 전환 시 Playground 응답 지연

## 증상과 확인 범위

Playground에서 100,000행을 선택하면 브라우저가 응답하지 않는 현상이 사용자 환경에서 발생했다. 당시 힙 사용량이나 브라우저 오류 로그는 확보되지 않아 메모리 부족 여부는 확인되지 않았다.

기존 Chrome 검증에서는 100,000행 중 데이터 행 18~23개를 DOM에 렌더링했다. 동시에 Playground 코드에서는 데이터 규모를 바꾸는 `onChange` 핸들러가 전체 배열을 동기적으로 생성하고 있었다. 이 작업이 끝날 때까지 브라우저 메인 스레드가 다음 입력과 화면 갱신을 처리할 기회를 얻지 못할 수 있어, 데이터 생성 경로를 수정했다.

## 변경 내용

- **작업 분할.** `prepareEmployees`는 128행 단위로 작업 시간을 확인한다. 한 타이머 콜백에서 약 4ms를 쓰면 남은 작업을 `setTimeout`으로 예약한다. 4ms는 다음 작업을 예약하는 기준이며, 개별 작업의 실행 시간 상한은 아니다. [mockData.ts](../apps/playground/src/demo/mockData.ts#L77)
- **반복 할당 감소.** 샘플 이름·이메일 조합과 날짜를 미리 만들어 각 행에서 참조한다. 행마다 새 객체와 고유 ID를 만들되, 반복되는 문자열과 `Date` 인스턴스의 생성을 줄였다. 전체 데이터 배열은 완성 후 메모리에 유지된다. [mockData.ts](../apps/playground/src/demo/mockData.ts#L46)
- **화면 갱신과 취소.** 데이터 생성이 끝날 때까지 기존 그리드와 준비 상태를 표시한다. 생성 완료 시 새 배열을 한 번 전달한다. 사용자가 다른 규모를 선택하거나 컴포넌트가 언마운트되면 effect 정리 함수가 예약된 생성을 취소한다. 표시되는 생성 시간은 각 작업의 실행 시간을 합산하며 타이머 대기 시간은 제외한다. [App.tsx](../apps/playground/src/App.tsx#L18)

## 검증 결과

- Vite 개발 서버에서 Chrome CPU 속도를 6배 느리게 설정했다. 100,000행 전환을 3회 반복해 준비 메시지, 최대 24개로 제한된 DOM 데이터 행, 마지막 행 이동을 확인했다. 생성 중 1,000행으로 빠르게 바꿨을 때 최종 표시가 1,000행으로 갱신되는 것도 확인했다.
- 타입 검사, ESLint, Prettier, Vitest 23개, 프로덕션 빌드가 통과했다. 사용자 환경에서도 수정 후 정상 전환을 확인했다.
- 수정 전후 힙 사용량은 측정하지 않았다. 확인된 결과는 위 조건에서의 전환과 스크롤 동작이다.
