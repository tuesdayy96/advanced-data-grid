# 10만 행 전환 시 Playground 응답 지연

## 증상과 결론

Playground에서 100,000행을 선택하면 브라우저가 응답하지 않는 현상이 사용자 환경에서 발생했다. 당시 힙 측정값과 브라우저 오류 로그는 확보되지 않았다.

임시 복제본에서 당시의 데이터 생성 방식을 복원하자, 100,000행을 만드는 동안 화면 갱신이 지연됐다. CPU를 6배 느리게 설정했을 때 메인 스레드의 최장 작업은 **356ms**였다. 재현 실험에서는 메모리 부족이나 탭 종료가 관찰되지 않았다. 측정 결과는 **동기 생성에 따른 일시적인 메인 스레드 점유**가 응답 지연을 일으킬 수 있음을 보여준다. 당시 사용자 환경에서 메모리 압박이 함께 발생했는지는 확인할 수 없다.

## 재현 방법

Phase 2 코드가 들어 있는 커밋 `dc0ec42`를 임시 디렉터리에 풀어 프로덕션 빌드 세 가지를 만들었다. 가상 스크롤과 렌더링 구조는 공통으로 사용했다.

1. **당시 방식 복원** — 데이터 개수 변경 핸들러에서 전체 배열을 동기적으로 생성했다. 이름·이메일 문자열과 `Date` 객체를 행마다 새로 만들었다.
2. **공유 데이터로 동기 생성** — 이름·이메일 조합과 날짜를 재사용하면서 전체 배열을 한 작업에서 만들었다.
3. **수정 방식** — 같은 공유 데이터를 사용하고 배열 생성 작업을 여러 타이머 콜백으로 나눴다.

Windows 11의 헤드리스 Chrome 157.0.8103.79에서 각 빌드를 기본 CPU 속도와 DevTools CPU 6배 감속 조건으로 실행했다. 빌드·CPU 조건마다 새 브라우저 컨텍스트에서 5회씩, 총 30회 100,000행으로 전환했다. 모든 실험용 소스와 빌드 산출물은 임시 디렉터리에 뒀다. 실험 전후 원본 저장소의 소스·문서 등 66개 파일의 SHA-256이 모두 일치했다.

## 측정 결과

별도 표기가 없는 시간은 5회 측정의 중앙값이다. 첫 화면 갱신은 선택 이벤트부터 첫 `requestAnimationFrame` 콜백까지, 데이터 표시 완료는 100,000행 상태에서 데이터 행이 DOM에 있는 첫 프레임 콜백까지 측정했다. 장기 작업은 Chrome의 Long Tasks API가 기록한 50ms 이상 메인 스레드 작업이다.

| -------- | ----------------------- | -------------: | -----------: | ---------------: | ---------------: |
| 기본     | 당시 방식 복원          |         56.0ms |       61.5ms |           61.6ms |             69ms |
| 기본     | 공유 데이터로 동기 생성 |         11.7ms |       15.0ms |           15.0ms |        기록 없음 |
| 기본     | 수정 방식               |          8.5ms |        3.1ms |           20.7ms |        기록 없음 |
| 6배 감속 | 당시 방식 복원          |        311.0ms |      333.8ms |          334.0ms |            356ms |
| 6배 감속 | 공유 데이터로 동기 생성 |         53.0ms |       76.4ms |           76.6ms |            100ms |
| 6배 감속 | 수정 방식               |         27.0ms |       15.1ms |          132.2ms |        기록 없음 |

| 생성 방식               | 생성 후 강제 GC 직후 JS 힙 중앙값 | 샘플링한 최대 JS 힙 |
| ----------------------- | --------------------------------: | ------------------: |
| 당시 방식 복원          |                            23.3MB |              25.8MB |
| 공유 데이터로 동기 생성 |                             7.5MB |               8.0MB |
| 수정 방식               |                             7.7MB |               9.2MB |

강제 GC 직후 힙 중앙값은 두 CPU 조건에서 소수점 첫째 자리까지 같았다. 최대 힙은 두 조건의 샘플 중 가장 큰 값이며, 작업 내부의 순간 피크는 별도로 계측하지 않았다. Chrome이 보고한 JS 힙 한도는 약 4.4GB였다. JS 힙 측정에는 브라우저 프로세스 전체 메모리와 당시 사용자 환경의 메모리 상태가 포함되지 않는다.

세 빌드 모두 100,000행 전환 직후 DOM에 데이터 행을 최대 18개만 유지했다. 30회 모두 마지막 행까지 이동했고 탭 종료나 페이지 런타임 오류는 없었다.

## 결과 해석

- 이름·이메일·날짜 재사용은 강제 GC 직후 JS 힙을 **23.3MB에서 약 7.5MB**로 낮췄다. CPU 감속 상태에서는 재사용만 적용한 동기 생성도 첫 화면 갱신까지 **76.4ms**가 걸렸고, 5회 모두 장기 작업이 기록됐다.
- 재사용 데이터를 그대로 두고 작업만 나누자 힙은 **7.5MB와 7.7MB**로 비슷한 수준이었고, 첫 화면 갱신은 **76.4ms에서 15.1ms**로 줄었다. 감속 조건에서도 장기 작업은 기록되지 않았다. 두 변형의 차이는 화면 응답이 작업 스케줄링에 영향을 받았다는 직접적인 근거다.
- 작업을 분할하면 브라우저가 중간에 화면 갱신과 입력을 처리할 수 있다. 그만큼 여러 작업이 완료되기까지 대기 시간이 생긴다. CPU 감속 조건에서 전체 데이터 표시까지는 동기 재사용 방식의 76.6ms보다 수정 방식의 132.2ms가 더 길었다.

## 적용한 수정

- **작업 분할.** `prepareEmployees`는 128행마다 경과 시간을 확인한다. 타이머 콜백에서 약 4ms를 사용하면 나머지를 `setTimeout`으로 넘긴다. 4ms는 다음 작업을 예약하는 기준이며, 개별 콜백의 실행 시간 상한은 아니다. Playground에 표시하는 생성 시간에는 타이머 대기 시간이 제외된다. [mockData.ts](../apps/playground/src/demo/mockData.ts#L79)
- **반복 할당 감소.** 이름·이메일 조합과 날짜를 미리 만든 뒤 여러 행에서 재사용한다. 각 행은 별도의 객체와 고유 ID를 갖고, 완성된 전체 데이터 배열은 계속 메모리에 유지된다. [mockData.ts](../apps/playground/src/demo/mockData.ts#L47)
- **준비 상태와 취소.** 생성 중에는 기존 그리드와 준비 상태를 표시한다. 생성이 끝나면 새 배열을 한 번에 전달한다. 사용자가 다른 행 수를 선택하거나 컴포넌트가 언마운트되면 예약된 작업을 취소한다. 별도 개발 서버 테스트에서 100,000행 생성 중 1,000행으로 전환했을 때 최종 화면에 1,000행이 표시되는 것도 확인했다. [App.tsx](../apps/playground/src/App.tsx#L37)
