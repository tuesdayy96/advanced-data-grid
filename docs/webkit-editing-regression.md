# WebKit 셀 편집 재진입 문제 분석

## 개요

Windows의 Playwright WebKit에서 셀 편집을 저장한 직후 F2를 누르면 편집기가 간헐적으로 다시 열리지 않았다. 실패한 경우에도 셀 선택은 유지됐고 그리드에 포커스가 있었다. Playground 프로덕션 빌드의 기본 100행 데이터에서 첫 번째 행(ID 1001)의 편집 가능한 Name 컬럼으로 재현했다. Playground는 `onCellChange` 콜백에서 전달받은 변경값을 앱이 관리하는 `rows` 배열에 반영한다.

## 재현 방법

1. 첫 번째 행의 Name 셀을 클릭하고 F2를 누른다.
2. 유효한 이름을 입력하고 Enter로 저장한다.
3. 새 이름이 셀에 표시되고, 테이블이 DOM 포커스를 가지며, `aria-activedescendant`가 같은 Name 셀을 가리키는지 확인한다.
4. 셀을 다시 클릭하거나 포커스를 옮기지 않고 F2를 누른다.

정상 동작에서는 저장한 이름이 채워진 입력창이 열리고 입력창에 포커스가 이동한다. 실패한 실행에서는 셀에 저장한 이름이 그대로 표시되고 입력창이 마운트되지 않았다.

진단 과정에서는 빈 값을 한 번 제출해 검증 오류를 발생시킨 뒤 유효한 이름을 저장했다. 아래 회귀 테스트는 검증 오류 단계를 생략하고, 프로덕션 빌드에서 같은 셀의 재진입을 확인한다.

```sh
pnpm test:e2e e2e/grid.spec.ts --project=webkit -g 'reopens the same editor' --repeat-each=30 --retries=0
```

## 조사 과정

브라우저에서 키보드, 포인터, `input`, `change`, 포커스 이벤트를 수집했다. 임시 라이브러리 빌드에서는 편집 세션의 시작·종료와 `useEffect` 실행 시점의 상태를 기록했다. 실패한 실행에서 관찰한 순서는 다음과 같다.

| 단계                    | 관찰한 이벤트 또는 상태                                                                                                                                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 첫 번째 F2              | Name 셀이 활성 상태였다. 테이블의 React 핸들러가 F2를 처리했고 입력창에 포커스가 이동했다.                                                                                                                                                      |
| Enter                   | 편집 핸들러가 입력값을 검증하고 세션 ref를 초기화한 뒤 편집 상태 업데이트를 예약하고 `onCellChange`를 호출했다. Playground도 행 업데이트를 예약했다. `finishNavigation`이 테이블에 포커스를 돌려줬고, 다음 DOM 커밋에서 저장한 이름이 표시됐다. |
| 두 번째 F2              | 브라우저의 `keydown` 이벤트가 포커스된 테이블에 도달했다. React 핸들러가 이벤트를 처리하고 기본 동작을 막았다. `aria-activedescendant`는 같은 Name 셀을 가리키고 있었다.                                                                        |
| 새 세션 시작            | 훅이 저장한 이름을 초기값으로 사용해 새 편집 세션을 생성했다.                                                                                                                                                                                   |
| 이전 렌더의 effect 실행 | 이전 렌더에 기록된 값은 `editing = null`이었고 검증할 대상도 없었다. ref에는 이미 새 세션이 들어 있었기 때문에 이전 effect가 이 새 세션을 닫았다.                                                                                               |
| 최종 DOM                | 저장한 이름은 셀에 남았고 테이블 포커스는 유지됐다. 입력창은 마운트되지 않았다.                                                                                                                                                                 |

이벤트 기록에서 F2가 의도한 테이블에 도달해 편집 시작 로직을 실행한 사실을 확인했다. 당시 행 키와 활성 셀은 유효했고, 앱이 저장한 값도 새 세션에 반영됐다. 증상은 이 세션이 생성된 뒤 이전 effect에서 종료되면서 발생했다. 해당 WebKit 빌드에서 이 실행 순서가 더 자주 발생한 이유는 확인하지 못했다.

## 근본 원인

[`useGridEditing`](../packages/react-data-grid/src/hooks/useGridEditing.ts)은 React 상태로 편집기를 렌더링하고, ref로 이벤트 처리 시점의 세션을 동기적으로 읽고 쓴다. 기존 `useEffect`는 렌더할 때 계산한 `targetExists`와 effect가 실행될 때 ref에서 읽은 세션을 함께 사용했다.

이전 effect가 실행되기 전에 F2가 들어오면 ref가 새 세션을 가리킬 수 있다. 이때 이전 effect는 편집 대상이 없다는 이전 렌더의 검증 결과로 새 세션을 종료한다. 그 결과 ref와 예약된 편집 상태 업데이트가 모두 초기화된다. React StrictMode 단위 테스트는 레이아웃 단계에서 새 세션을 시작하고 그 뒤에 이전 렌더의 effect가 실행되도록 해 같은 순서를 재현한다.

## 수정 내용

effect가 실행될 때 ref에 담긴 세션과 해당 렌더에서 기록한 세션이 같은 객체인지 확인하도록 했다. 세션이 같을 때만 해당 렌더의 검증 결과를 적용한다. 새 세션은 그 세션을 렌더링한 effect에서 기존 방식대로 대상 유효성과 화면 렌더링 범위를 검사한다. 공개 API, 포커스 대상, 키보드 이동, 앱의 행 업데이트 및 가상 스크롤 동작은 기존과 같다.

```ts
const session = current.current;
if (session !== editing) return;
```

회귀 테스트는 저장 및 Escape 취소 후 같은 셀에서 편집기를 다시 여는 경우와 ArrowRight 또는 Shift+Tab으로 이동한 뒤 편집을 시작하는 경우를 확인한다. 같은 셀의 재진입 테스트는 F2를 다시 누르기 전에 저장된 텍스트, 활성 셀, 실제 포커스를 확인한다. 세션 동일성 검사를 제거하면 StrictMode 테스트가 실패한다.

## 검증 결과

수정 전후 재현은 Windows 25H2(빌드 26200), Node.js 24.19.0, React 19.3.1, Playwright 1.65.1에서 Playground 프로덕션 빌드로 진행했다. 헤드리스 브라우저에서 매 시도마다 새 페이지를 열고 키보드 입력을 전달했다. 저장한 값이 보이고 그리드가 다시 포커스를 받은 뒤 F2를 눌러 편집기가 열리는지 기록했다. 실패율은 전체 시도 중 실패가 차지하는 비율이다.

| 브라우저                   |  수정 전(통과 / 실패) | 수정 후(통과 / 실패) |
| -------------------------- | --------------------: | -------------------: |
| WebKit 27.2                | 13 / 17(실패율 56.7%) |               30 / 0 |
| Chromium 159.0.8154.6      |                 5 / 0 |                5 / 0 |
| Firefox 159.0              |                 5 / 0 |                5 / 0 |
| Windows Edge 157.0.4341.60 |                미측정 |                5 / 0 |

Phase 7.5에서 관찰한 5회 중 3회 실패는 별도 실행 결과다. 로컬 tarball을 설치한 소비자 앱의 프로덕션 빌드에서도 앱이 직접 행 상태를 관리하도록 구성했다. React 18.3.1과 19.3.1에서 WebKit 재진입 테스트가 각각 5회 모두 통과했다.

- **WebKit 전용 회귀 테스트** — 재시도 없이 별도로 30회 실행해 모두 통과했다.
- **전체 Playwright** — 74개 통과, 기존 Firefox axe 검사 2개 건너뜀. Chromium, WebKit, Edge에서 각각 19개, Firefox에서 17개가 통과했다.
- **Vitest** — StrictMode 회귀 테스트와 accessor 호출 횟수 검사를 포함해 112개가 통과했다.
- **정적 검사와 빌드** — TypeScript, ESLint, Prettier, 라이브러리 및 Playground 빌드가 통과했다.

수정 후 Chromium 성능 테스트는 100,000행 시나리오 5사이클을 통과했다. DOM에 마운트된 데이터 행은 최대 21개였다. Playwright 동작 시간의 중앙값은 편집기 열기·입력·취소 49.8ms, 그리드 양 끝으로 이동 106.0ms, Shift 범위 선택 18.6ms, 키보드로 컬럼 너비 조절 27.3ms였다. 이 수치에는 브라우저 자동화 시간이 포함된다. 편집 확정과 재진입은 정상 동작 여부를 확인했으며, 개별 지연 시간과 동일 조건의 수정 전 기준값은 측정하지 않아 시간 차이는 판단할 수 없다.

## 검토한 대안

테이블에 포커스가 돌아오는 것이 로그에서 확인됐으므로 포커스 복원 시점을 옮겨도 세션 불일치 자체는 해결되지 않는다. 테스트에서 셀을 다시 클릭하거나 강제로 포커스를 주면 사용자가 겪은 입력 순서를 재현할 수 없다. 타이머나 재시도는 다음 시도 전에 문제가 발생하는 시점이 지나가기를 전제로 한다. 세션 동일성을 검사하면 이전 effect가 새 세션을 종료하는 경로를 직접 차단할 수 있다.

## 조사에서 확인한 점과 검증 한계

DOM 포커스, 활성 셀, 편집기 마운트는 각각 관찰해야 한다. 이 사례에서 포커스가 돌아왔다는 사실로 키보드 탐색 상태는 확인할 수 있었지만, 편집기가 열리지 않는 이유를 설명하려면 추가 기록이 필요했다. React 키 이벤트의 처리 결과와 effect가 참조한 렌더 상태 및 세션 ref를 함께 확인해 편집기를 닫은 시점을 찾았다.

반복 검증은 헤드리스 브라우저에서 수행했다. 실제 macOS Safari, 보조 기술 수동 사용, 운영체제 IME 입력은 이번 검증 범위에 포함되지 않았다. 자동화된 IME 동작 검사는 Vitest에 포함되어 있다. Windows Firefox는 이 작업 환경에서 axe 평가 중 브라우저가 종료되는 문제가 있어 해당 검사를 건너뛰었다.
